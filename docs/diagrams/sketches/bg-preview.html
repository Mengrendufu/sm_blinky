布局锚点按 screen-ebike 版生成：顶栏 y0–24、大环 (40,28)–(200,188) 圆心 (120,108)、两张卡 y204–296、底栏 y304–320。 每张 240×320，两种形态：.png（给你看）与 .rgb565（LVGL 原生格式，153,600 B/张）。

绿框=背景露出来的区域（顶栏、环周围、卡片间隙、底栏）； 红框=被不透明控件盖住的区域（两张卡）—— 那部分画得再好也看不见，除非把卡片改成半透明（LV_OPA_80）。

线速账（18 MHz SPI、每张 153,600 B）：68.3 ms/张、三张 204.8 ms；实测（2026-10-10，BSP_dbgBootMs_ 标记差）： payload 读 263 ms（1.75 MB/s，差的 ~58 ms 是分块开销；块已试到 32→64 KB 上限、无改善 ✗）+ CRC32 205 ms（逐字节）⇒ 资产段合计 468 ms，加面板段 411 ms ⇒ 暖复位到资产就位 879 ms。
可压的两处：① 槽 1 目前不显示，去掉它可省 ~155 ms；② CRC 要提速得动 3rd_party/common_c。

④ flash 里存什么格式（2026-10-08 已定案 = B1；B2/B3 评估后未采用，留作对照）

方案flash 占用启动加载LVGL 侧代价
B1 · 裸 RGB565（采用 ✓）460,800 B（450 KB）204.8 ms 线速 / 实测 263 ms SRAM 里就是原生格式，lv_image_dsc_t 直接指过去，零解码flash 占 450 KB
B2 · RLE 压缩 + 启动解压到 SRAM≈ 12–28 KB/张，合 ≈ 60 KB flash 读 ≈ 27 ms + 解压（未实测）解压后同样是 SRAM 里的原生 RGB565，LVGL 无感 要在 app 里写解压；多一段 CPU 时间
B3 · 让 LVGL 直接读压缩资产≈ 60 KB0（不预载） LVGL 每帧逐像素解码不建议每帧解码 + 混合，刷新会被拖垮
RLE 游程数（4,150 / 9,551 / 9,078）是按"相邻像素相同"直接数的，没有真实编码器；B2 若真做还要算长度字段与解码耗时。

⑤ 文件在哪 / 怎么烧 / 怎么核

图源与产物：./bg/ 共 8 个文件（bg-a / bg-b / bg-c / bg-logo 各一份 .png + .rgb565，小端 RGB565）。
生成器：gen_bg.py（三张背景）+ gen_logo.py（开机图），都在本目录，纯标准库；本页由 gen_bg_preview.py 生成。
烧写：tools/burn-asset.py（Windows 侧，CH340 = COM12）把三槽拼成 460,800 B 经 bootloader 写进 NOR 0x00081000。
核验（三方对齐）：烧完读 app 的 Asset_.crc32（J-Link）＝ SRAM 槽头 ＝ 仓库拼出来的 0x7BE8D093 ✓。
