# AST2 资产存储与验证

整包烧写，逐图校验；不支持单图更新。当前仍为最多三个固定大小槽位，
每槽 153,600 B（240 × 320 × RGB565），ID 依次为 Sys、Live、Splash。

## 文件与 NOR 布局

脚本输入为按槽位拼接的 RGB565 裸数据；`burn-asset.py --image`
自动构造 AST2 包。也可以离线生成以供检查：

```sh
python3 tools/asset_pack.py /tmp/images.rgb565 /tmp/assets.ast2
```

离线输出不是 `--image` 的输入；该参数始终接收裸数据，避免重复封装。

NOR 基址保持 `0x81000`，目录独占 4,096 B 扇区，像素从 `0x82000` 起。
三图包长 464,896 B，其中像素 460,800 B；NOR 结束地址为 `0xF2800`
（不包含），不侵入从 `0x100000` 开始的 NVS。

目录共 68 B，所有字段均为大端 uint32，不直接序列化 C 结构体：

| 偏移 | 内容 |
|---|---|
| 0 | Magic：`AST2`（0x41535432） |
| 4 | 格式版本：2 |
| 8 | 图片数量：1～3 |
| 12 | 像素总字节数 |
| 16～63 | 三条 16 B 目录项：ID、像素相对偏移、长度、图片 CRC32 |
| 64 | 前 64 B 的 CRC32 |

未使用目录项必须全零。图片偏移相对像素区域，固定为 ID × 153,600，
长度固定为 153,600。目录扇区其余部分在包文件中填 0xFF。
CRC32 使用与 Python zlib 相同的算法；图片 CRC 覆盖最终 RGB565 字节。
格式定义与目录检查由 `shared/asset_format.h` 在 BL/App 间共享。

## 烧写责任

上位机生成各图的期望 CRC 和目录 CRC。UART 协议版本升级为 2，
握手长度包含目录扇区；块索引 0 为目录，后续块为像素载荷。
块校验及最终整包传输 CRC 仍保留，用于传输完整性。

BL 接收并验证目录后，先擦除旧目录，将新目录暂存在 RAM，随后按顺序
擦写像素块，并逐块读回 memcmp。丢 ACK 后重发最后一块只应答，不重写、
不重复累计长度或 CRC。索引、块长和总长均受握手及分区约束。

最终传输检查通过后，BL 从 NOR 逐张重读并校验图片 CRC，全部通过才
写入目录并读回验证，随后应答并复位。替换中断会失去旧包；这里没有
双份资产或旧版本回滚承诺。目录 CRC 用于拒绝不完整或损坏的元数据。

## App 加载责任

目录读取与校验最多尝试三次。有效后先加载 Splash，再加载正常页图片。
每张图最多三次「读取到 SRAM → 对 SRAM 副本计算 CRC32」。读取失败
或 CRC 不匹配都会重试；耗尽后该图访问器返回 NULL，页面使用纯色背景。

Splash 在自身校验通过后才可借用；进入第二阶段后不再改写其 SRAM，
其他图片失败也不会撤销它。每张正常页背景独立可用；`Asset.present`
表示目录声明的全部图片都通过校验，`Asset_slot` 按单图有效性返回指针。
两个阶段处理完成事件仍沿用现有 HSM 路径，失败不会让 UI 永久等待。
Flash AO 完成本阶段写入后再投递事件；UI 收到第一阶段完成后才读取
Splash/元数据，收到第二阶段完成后才读取正常页资产及 present。
已交付的结果保持不变，不支持运行期重加载；访问器及标志写入不再
使用临界区，跨线程发布由事件通道负责。

Trace 45 仍为 5 B：第一个字节表示所有图片是否通过，后四字节改为
大端图片有效位图（bit0/1/2 对应三个 ID），不再表示旧格式的整包 CRC。

## 迁移和验证

AST1 不兼容；新 App 遇到旧资产会使用纯色降级页面。需要将 BL、App
及外部 Flash 资产一起升级至 AST2，不能只更新某一端。

```sh
python3 tests/test_asset_loop.py
```

宿主测试执行实际 BL 协议及 App 加载器，UART/NOR/调度器为桩，SRAM
使用宿主映射。覆盖脚本生成的 1/2/3 图包、重复块、读取失败、瞬态和
永久 CRC 错误、坏目录、错误索引、传输校验失败、无握手及替换中断。
通过 ASan/UBSan；不代表已完成板端串口烧写、性能或掉电测试。
