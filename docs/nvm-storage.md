# 应用 NVM 映射与事件写入

application/nvm 是应用共享模块；数据布局、逻辑 ID 与 NVS key 的
对应关系集中在这里。Flash AO 不定义业务 key，不维护 checkpoint。

## 静态映射

模块只保留 nvm.h/nvm.c，实际数据各自声明类型和静态实例。
只读信息头数组 Nvm_meta_ 只登记 data 和 size，
不要求数据是 uint32_t，也不通过整块结构的 offset 定位。
应用 ID、信息头下标、NVS 记录 ID 完全一致；0 为应用约定的无效项，
既有 ID 1/2 固定。不另存 key 映射。

| ID / 下标 / NVS ID | 当前数据 | 当前长度 | 恢复动作 |
|---|---|---|---|
| NVM_BOOT_COUNT = 1 | Nvm_boot_ | 4 B | 复制 |
| NVM_BLINKY_EDGES = 2 | Nvm_blinky_ | 4 B | 复制 |

Nvm_meta(id) 提供只读信息头，实际 RAM 访问仍遵守模块接口的同步契约。
未登记的 ID 返回 NULL。恢复遍历有效下标，保存直接使用事件 ID。
所有登记项都参与启动恢复。NVS 记录完整通过读取、长度及 CRC 校验
后，恢复流程统一 memcpy 到信息头指定的 RAM 快照；meta 没有恢复
回调，也不能按项选择是否恢复。结构体、数组等数据都遵循同一流程。

IO 使用 Nvm_IoBuffer 联合体作为临时缓冲，容量和对齐由所登记类型
决定，无固定 4 B 数据上限、VLA 或堆分配。新增数据类型时，将该类型
加入缓冲联合体，再登记实际变量的地址和 sizeof；若漏配
缓冲容量，IO 返回 -EOVERFLOW，不进行越界复制。
写入结果另行保存，不混入只读信息头。

NVM 模块的 RAM getter/add 不访问 NOR；薄 IO 由 Flash AO 串行执行。
原有 Flash_nvsRead/Write 任意 key RPC 已撤下，外部应用不再传物理 key。
裸区读、写、擦的同步 RPC 保持不变。

## 启动恢复

Flash 完成资产加载后挂载 NVS，调用 Nvm_load 按表读取各项。
缺项保留数据初始化的默认值；异常长度或 IO 错误返回失败，
读回内容只有完整通过长度和 NVS CRC 校验才交付，其他有效项仍恢复。
Nvm_restore_ 只负责通用复制。其外层应用初始化在恢复结束后将暂存
的 LED 增量合入快照，并将启动次数加一。恢复期间的应用计数先进入
独立增量区，避免复制覆盖；这属于业务数据交互，不是逐项恢复策略。

启动路径不主动保存这些应用项。启动次数也等应用事件触发才落盘，
因此首次保存前复位不会记录本次启动。NVS 原有 mount/clear 恢复逻辑
保留，属于存储初始化；不代表启动时写入应用字段。
启动 trace 91 的 tag 为 3：mount 耗时、恢复成功标记、恢复耗时、
启动次数低两字节和 tag；不再报告启动写入耗时。

## 业务快照与页面显示

Blinky 在 ON/OFF entry 每次计入一个边沿，先调用 Nvm_addBlinky，
再投递 UI LED 事件；初始进入 ON 也计入，延续原有计数口径。
恢复前的增量暂存于 NVM 模块，恢复后合入持久化基值。
Live 只在入页和刷新时通过 Nvm_blinky 读取全局快照，
UI 自身的 ledEdges 仅用于显示模型及栈报告，不再发布 NVM 增量。
累计和定期保存均不依赖当前页面，也不依赖 UI 是否排空收件箱。

## 应用触发的按项写入

```text
Blinky 每 20 次 500 ms 节拍
  → Flash_postNvm(FLASH_NVM_WRITE_SIG, Nvm_Id)
  → SST_NEW 动态事件，信号 + Nvm_Id
  → Flash ready 状态直接消费
  → Nvm_store 按 ID 取 meta，在 RAM 临界区按 size 复制该项数据
  → 退出临界区，nvs_write 对应 key
  → 记录该项结果，SST 在派发结束后 GC 回收事件
```

Flash 不设置保存计时器，也不自投递下一次写入。
Blinky 保留每 10 s 的应用策略；每次分别投递两个逻辑项。
未初始化完成时返回未接收，应用在下一周期重试。

每次投递独立分配一个 Flash_NvmEvt；载荷只有逻辑 ID，操作由
SST_Evt.sig 决定。目前支持 FLASH_NVM_WRITE_SIG，不携带业务数据指针。
没有逐项静态事件表或 pending 标记，同一 ID 的多次请求分别排队。
保存内容取自处理时的 RAM；快照后的修改留待后续请求。
没有跨项事务或整包原子性承诺。

Flash 队列固定为十个槽位，不再由 NVM 项数决定。生产者遵守 SST 的
队列容量契约；事件池不足或队列满按既有契约断言处理。
目标 SST 事件池按需分两档：小池 4 B × 48、中池 8 B × 16，
共 320 B；现有事件没有大载荷，暂不创建大池。动态分配来自静态
内存池，不使用堆。小池预算为 UI 队列 32 + AO 队列 8 + 8 个在途
位置；中池预算为 Flash 队列 10 + 派发/生产者 + 4 个余量。SST_Task_post 获取引用，处理后
SST GC 回收。未完成初始化的投递返回未接收，不分配事件。
新增 NVM 项在 NVM 模块维护数据、ID、映射及初始结果；Flash 不改动。

投递成功只表示已入列，Nvm_writeResult(id) 查询最近完成的保存结果：
-EAGAIN 为尚未尝试，0 为成功，负数为 IO 失败。新请求排队时保留上一
完成结果，不用此接口判断某次请求是否完成。NVS 数据未变化而返回
0 同样算成功；失败不在 Flash 内部自发重试，后续仍由应用触发。

## 验证

```sh
python3 tests/nvm/run.py
python3 tests/ui_components/run.py
```

NVM 测试覆盖旧 key 兼容、缺项、异常长度、读失败、恢复期间并发增量、
写入期间 RAM 变化、未变化返回值、写失败与结果查询。
事件测试使用实际 Flash HSM、请求入口、Blinky 维护动作、发布订阅、
UI 收件箱和 SST GC；
覆盖启动期间不写入、按 ID 路由、同项独立排队、全部队列槽位占用、
裸区 RPC 成功/失败、通知后信封仍有效直到 GC、动态事件引用及循环回收，
以及第 20 拍由应用触发保存。
UI 宿主场景继续覆盖 NVM 计数显示；外设与任务调度由桩代替。
本轮仅宿主测试和实际头文件语法检查，没有构建或烧录固件。

类型扩展测试仅在临时副本中登记一个包含数组的 32 B 结构体，验证
meta 长度、统一复制恢复、缺项/失败保留默认值，
以及写入期间业务
修改不影响已捕获的 IO 快照。固件不增加测试字段或额外持久化项。

Flash 发出的两阶段就绪通知也由事件池分配。AO 发布与 UI 定向投递
各自分配、各自移交事件，避免 publish 结束时的 GC 影响后续投递。
测试覆盖有/无订阅者及接收方立即消费，最后重新分配两档的全部块，
确认就绪通知与运行期请求都已归还事件池。

全部非时间事件统一采用池分配，包括 Flash 启动/后续加载自投递、
UI GO/REFRESH 和裸区 RPC 信封。时间事件保留静态节点及事件。
裸区请求及缓冲仍按调用者借用语义交付，完成通知后不再访问请求，
信封留到 AO 派发返回后由 SST GC 回收，不再维护独立静态信封数组。
分级池按块大小升序注册，分配器选择首个能容纳事件的池；该池耗尽
遵循现有断言契约，不自动借用后续大池。未来新增更大事件再增大规格，
同步调整 SST_EVT_POOL_NUM 并登记新池。
宿主是 64 位指针布局，Flash_Evt 的测试中池按其 sizeof 分配；
目标平台的 4/8 B 容量另通过 ARM 编译期布局检查验证。


Flash 时基已统一为 HAL_GetTick（TIM1）：SPI 标志轮询、设备 BUSY
等待及启动诊断计时均不再依赖 DWT。App 的数据恢复在调度器之后，
Bootloader 烧写时也保持 HAL tick 中断运行，因此删除旧的 DWT 分支。
烧录和复位脚本无需保留调试使能位，恢复默认 J-Link 关闭行为。

默认 J-Link 关闭行为的板端复测通过：断开后运行 14,075 tick，NVS
写指针继续推进；复位后启动次数 115 → 116，累计值恢复最近保存值。
两档事件池最低剩余 45/48、14/16，故障寄存器为零。证据归档在
/tmp/hal-tick-board-0ahhmaa8/report.md；未重烧 SPI 资产或验证冷上电。
