# sm_blinky 项目章程

起草：2026-09-17（HEAD `2cb48c3`）。随增量推进更新；与 `AGENTS.md` 的分工是：`AGENTS.md` 记"现在是什么样、坑在哪"，本文件记"为什么这么走、下一步走到哪、验收看什么"。

历史中的旧 API、DWT 初始化方案和事件/队列形态不作为当前约定。

## 1. 阶段目标（可验收的 DoD）

1. 屏上有一个**事件驱动**的状态页：LED 状态、LCD/SRAM 两个探针结果、内存水位。
2. Blinky 管理 LED 与业务快照，通过事件通知 UI，不调用 LCD。
3. UI 线程自有收件箱；AO/ISR 不调用任何 `lv_*`。
4. 显示适配层提供帧耗时读数；Flash 超时与启动诊断统一使用 HAL tick。
   §13 保留 DWT 历史实验，当前实现不依赖 DWT。
5. 全静态分配，栈尺寸由 `[MEM][STACK]` 水位定量；记录 BSP 与任务装配
   耗时，不将它们解释为上电到首帧时间。

## 2. 范围

做：UI 线程骨架（普通线程 + 内嵌 HSM）、显示适配层（tick / flush / buffer）、LCD 绘制 API（规划名 `set_window` / `push_pixels` / `backlight` ⇒ **落地名 = `BSP_lcdSetWindow` / `BSP_lcdWritePixelsDma` / `BSP_lcdBacklight`** ✓）、事件契约与收件箱。

本阶段不做：触摸与输入设备（`flush_wait_cb` 的位置与**阻塞语义**已在增量 5 落地，见 §11）；多状态菜单（先 `Ui_running` —— **落地成了 `Sm_Ui` 的 Demo 页** ✓ + 一个状态页）；LVGL 池往外挂 SRAM 迁（与 DMA 一起定）；图片/字体资源管理。

| 资源 | 谁持有 | 谁可以写 |
|---|---|---|
| 屏（FSMC NE4） | `BSP_init()` 一次性 bring-up | 运行期只有 UI 线程 |
| 板载 SRAM（NE3） | BSP 初始化，Flash 加载资产 | UI 只读已发布图片 |

### 显示资产的热路径（flash → SRAM，历史设计与测量）

此处保留早期方案与吞吐证据。当前 Flash AO 两阶段 DMA 加载后发布
只读图片，UI 不执行加载循环；最新所有权与时序见 §28。

图片的冷存储是 SPI flash、热数据在外挂 SRAM。flash 的一端由**独立线程**持有（它不只存图片，还要放升级镜像与配置），SRAM 的一端仍在 UI 线程手里，于是这条链路上有一次**跨线程交接**——按借用语义做：调用者给缓冲、等待期间不碰、flash 线程在窗口内独占写、完成后归还，因此既不需要锁，也不需要双缓冲。两条线程形状同构，各自的理由不同：

- UI 线程的收件箱是**自建环 + 非阻塞投递**（`Ui_post*`），不像 SST AO 那 8 格队列——长活儿不会把它顶爆，只会推迟排空。
- 长读**分片**：每轮循环读一块（比如 4 KB）进 SRAM，把「阻塞」摊成有界的几毫秒，渲染与收件箱照常推进。不用额外任务。
- flash 的串行化由那一个线程本身提供：不管有多少消费者（资产、配置、标定），请求都在它的收件箱里排队，SPI2 总线上天然只有一个使用者。

两个前置条件：

- **传输粒度（2026-10-10 已做）**：原来是**每字节一次 HAL 调用**，函数开销把吞吐压到 **0.21 MB/s**。现在命令/地址仍逐字节、数据段走整块（`HAL_SPI_Transmit` / `HAL_SPI_Receive`，一次 ≤32 KB）✓。**实测（2026-10-10 重测，tick 计时 + 正确性交叉验证 `bad = 0`）**：逐字节 **4.8 µs/B**、HAL 轮询块读 **1.71 µs/B**、**DMA 0.44 µs/B（= 18 MHz 线速）** ⇒ **瓶颈是 HAL 的逐字节轮询，不是总线；只有 DMA 摸到线速** ✓。旧数字（逐字节 458 ms / 分块 196 ms / 2.35 MB/s）**作废** ✗：2.35 超过线速上限 2.25，是 TIM1 回卷口径污染的产物。验证是**投毒式**的：先往外挂 SRAM 写 0xDEADBEEF，复位后固件必须把它读没、CRC 仍要过 ——因为 SRAM 在热复位后**保留旧数据**，旧代码里读失败和读成功**长得一模一样**；现在 `BSP_flashRead` 会把 SPI 状态抛上来 ✓。
- **分片加载状态机（仍未做）**：读大资产要能在 UI 循环里「读一块、让出、下一轮接着读」，等运行期按需读资产时才需要。

flash 这一侧**确定要走 DMA**（与刷屏同构：提交 → 阻塞等完成中断 → 回调里收尾），于是两个热点都是「真阻塞」，§7 那条「让出 CPU 给 idle」自动成立。做之前先把五条硬约束记下来：

- **走 HAL 的 `_DMA` 入口，不自己搓通道**：收尾放在 `HAL_SPI_TxRxCpltCallback`（拉高 CS → `vTaskNotifyGiveIndexedFromISR`）与 `HAL_SPI_ErrorCallback`（HAL 的 `SPI_DMAError` 已先 abort 两个通道；这里关事务、标失败、同样唤醒），`HAL_SPI_TxRxHalfCpltCallback` **故意留空**——知情接受每次提交多一次 ISR 入口。连带两条必做：arm 前清 OVR（读 DR + 读 SR）与清 `DMA_IFCR` 标志，否则残留的 `TCIF` 会造成"假完成"。
- **DMA 通道会撞车**：SPI2_RX/TX 是 `DMA1_Ch4/Ch5`，而 **USART1_TX/RX 也是 Ch4/Ch5**——tracer 正走 USART1。哪天要把串口输出也 DMA 化，二者必须二选一或串行化。
- **只能 2 线 + 0xFF 哑元 TX**：STM32 的 1 线只收模式走 MOSI，而板上 flash 的 DO 接在 MISO(PB14) ✗，所以 RX DMA 必须配等长的 0xFF 哑元缓冲（静态 1~4 KB，进内部 SRAM 预算）。
- **CS 跨整段保持低**：命令+地址由 CPU 直发，数据段交 DMA，**完成中断里再拉高 CS**（ISR 写 GPIO 合法）。现有 `BSP_flashReadArray_` 是一次事务一进一出，要改形状。
- **RX 目的地址可以直接写外挂 SRAM**（0x68000000 区），热数据不占内部 RAM——这就是「flash → SRAM」最干净的一条路。DMA1_Ch4/5 的 handler 要加进 `stm32f1xx_it.c`，NVIC 优先级落在 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 之下（中断里要 `vTaskNotifyGiveFromISR`）。

**两条热路径的通道是分开的**，这点别混：刷屏走 FSMC（8080 并行），flash 走 SPI2，各自独立、可以并行。**共用一个 DMA 外设（DMA1）、走不同通道**：

- flash：SPI2 的请求线是固定的 → `DMA1_Ch4`(RX) + `DMA1_Ch5`(TX)
- 刷屏：**M2M 模式**（源=绘制缓冲、目的=LCD 数据地址）不用外设请求线，**任意空闲通道**都行 → 取 `DMA1_Ch6`

DMA1 共 7 个通道，当前占 3 个，余量按用途预留（RM0008 Table 78）：

| 用途 | 通道 | 备注 |
|---|---|---|
| flash 读 RX / TX | `DMA1_Ch4` / `Ch5` | SPI2 只在这两条（与 USART1、I2C2 共用请求线） |
| 刷屏（M2M） | `DMA1_Ch6` | M2M 不受请求线限制，任意空闲通道都行 |
| 预留 ADC1 | `DMA1_Ch1` | ADC1 只能在 Ch1，别占 |
| 预留 SPI1 | `DMA1_Ch2` / `Ch3` | 第二组 SPI（如 VS1053 口、另一块屏） |
| 备用 | `DMA1_Ch7` | I2C1 / USART2 / TIM4 等 |

DMA2（5 通道）是另一份余量：SPI3 → Ch1/2、UART4 → Ch3/5、SDIO → Ch4、ADC3 → Ch5、TIM5/6/7/8 与 DAC1/2 分布其中。上 SD 卡、SPI3、UART4 都不占 DMA1。唯一会撞的是 **USART1 与 flash 共用 Ch4/5**（详见下段）。通道优先级建议刷屏 > flash（刷屏对抖动更敏感，flash 是批量搬运）。

**flash 的读不能用 MEM2MEM，刷屏可以——判断标准是「端点有没有硬件握手」**：MEM2MEM 的语义是不等外设请求、软件一开就跑。SPI2 的数据寄存器是单字节寄存器加请求线握手，18 MHz 下 444 ns 才换一个新字节，而 M2M 下 DMA 约 28 ns 就操作一次 DR——RX 会读到重复的旧字节，TX 会把 DR 写爆 ✗。刷屏的两个端点都**不是**握手型：源是内部 SRAM，目的地是 FSMC 上的地址，FSMC 用等待状态自己限速，所以怎么快都不丢 ✓。

一句话准则：**内存映射的端点（SRAM、FSMC 上的 LCD/SRAM 器件）→ 任意通道、可 M2M、CPU 直读也行；握手型外设（SPI/USART/I2C）→ 只能用它固定的那一两条通道、走请求线**。（若这块 NOR 是 FSMC 上的并行 NOR，它就内存映射了，连逐字节 HAL 调用这个瓶颈都不会有；W25Q 是 SPI 器件，不是内存映射。）

热路径的字节流向（谁搬、谁限速、谁收尾）：

```
W25Q 阵列  --串行 18 MHz, 1 字节/444 ns-->  SPI2 移位寄存器
   -> SPI2->DR（RXNE 置位 = DMA 请求）  -> DMA1_Ch4 读 DR、写目的地
   -> AHB 总线矩阵 -> FSMC（按 SRAM bank 等待状态限速）-> 外挂 SRAM 0x68000000
回程时钟：DMA1_Ch5 把内存里的 0xFF 哑元搬进 SPI2->DR（TXE 请求驱动，不决定快慢）
控制面：CS 由 CPU 管——提交前拉低、命令+地址 CPU 直发、完成中断里拉高并唤醒线程
```

带宽账：SPI2 @18 MHz = **2.25 MB/s 是真正的瓶颈**；DMA1 约 72 MB/s、FSMC→SRAM 在器件安全档下 **24.0 MB/s 读 / 20.6 MB/s 写**（ADDSET=1，读 DATAST=1、写 DATAST=3；原来的 8 MB/s 是「功能探测」时序 ADDSET=1/DATAST=15 的账面值，从未实测）。读侧 DATAST 的下限是 1（RM0008 Table 112：*cannot be 0*），给 0 会让 FSMC 卡死整机——这条已上板验证过。所以一条 4 KB 分片 ≈ 1.8 ms，1 MB 资产 ≈ 0.44 s——**优化 SPI 以外的任何环节都没有意义**。两个细节：SPI 可配 **16 位帧**（一次 DMA 搬 2 字节，代价是字节序变成先收的在高位）；**读**是连续流、不受 256 字节页边界限制（只有页编程有）。

为什么不用 DMA2：**flash 根本换不过去**。RM0008 Table 78（p.282）里 SPI2 只出现在 DMA1：`SPI2/I2S2_RX → DMA1_Ch4`、`SPI2/I2S2_TX → DMA1_Ch5`。请求线是硬连线，表里的 `SPI1`、`SPI2/I2S2`、`SPI/I2S3` 都是**具体外设编号**（`I2Sx` 只是同编号外设的另一种模式），不是「任意 SPI」。一条通道服务一组固定外设（Ch4 = `SPI2/I2S2_RX` + `USART1_TX` + `I2C2_TX`），它们**共用同一条请求线，同一时刻只能启用一个**。

刷屏走 M2M（表里每通道都写着 SW trigger/MEM2MEM），**不受请求线约束**，任意空闲通道都行——这是它自由度大的原因。放 DMA2 收益很小：一个控制器一次只服务一个通道（按优先级分时），而 DMA1 约 72 MB/s，我们 flash 只要 2.25 MB/s、刷屏突发约 28.8 MB/s，远没饱和；DMA2 还要多开时钟与中断。

**更正**：DMA2 **不能**拿来放 USART1 —— 同页原文列出 DMA2 的请求来源只有 `TIMx[5,6,7,8] / ADC3 / SPI-I2S3 / UART4 / DAC1,2 / SDIO`，其中没有 USART1（那是 F4 一类芯片才有）。所以在 F103ZET6 上 USART1 只能在 `DMA1_Ch4/5`，**和 flash 硬撞**。tracer 若真要 DMA，只有三条路：与 flash 分时复用 Ch4/5、把控制台换到 USART2/3 或 UART4（看板子怎么接）、或者不上 DMA（现状）。

唯一共享的是**目的地**：flash 的数据若落在外挂 SRAM，那条 DMA 也要过 FSMC，于是**只有两条 DMA 同时在飞时**才会在 FSMC 控制器上互让；串行执行（UI 线程一次做一件事）时不存在这个问题。是否让它们重叠是显式选择：重叠更快，但要在 FSMC 上互相排队。另注意 **USART1_TX/RX 也占 DMA1_Ch4/5**——tracer 哪天要上 DMA，就会和 flash 撞，必须二选一。

**该例外已于 2026-10-10 彻底消失**：`fwt` 自检任务与全部硬件探针删除 ⇒ 运行期**只有 flash 线程碰 flash**，「总线只有一个上下文」第一次真正成为不变量 ✓。

### flash 的两种生命周期（多方共享资源）

flash 不只是 UI 的资产存储：它还要放**升级镜像**、**配置/KV**、出厂标定。所以所有权的粒度不是「整片」也不是「按分区分配所有权」——**SPI2 总线本身是不可分割的独占资源**，两个上下文即使碰不同分区，也会在总线上撞车（一次事务被插进来，命令/地址/数据序列就错位了）。

| 生命周期 | 谁持有 flash | 干什么 |
|---|---|---|
| **启动早期**（调度器/UI 之前） | BSP / 升级流程**独占** | 探测、整片操作、固件升级（擦写暂存区、校验、写内部 flash） |
| **运行期** | **flash 线程独占** | 热路径 flash → SRAM 的读（资产），以及配置/KV 的写 |

由此三条规矩：

1. **升级不挂运行期的两个线程**：它是长操作、要独占、可能要整片擦；放进 UI 线程等于让「用户切页」和「擦写几百 KB」互相打断，放进 flash 线程等于让所有读请求在整片擦的十分钟里排队。升级是独立生命周期——开机早期跑，或由维护模式触发（那时 UI 不启动/已停用）。
2. **运行期只读资产**。运行期唯一可能的写是配置/KV，也走 flash 线程的请求接口，保证运行期只有一个写者（形态与代价见 §8.6）。
3. **分区管的是「谁能写哪一段、擦除粒度多大」**，不是并发。分区表提案（数字待定）：meta 4 KB / update A、B 各 256 KB / assets 8 MB / config 128 KB / factory 4 KB / 其余保留。

前置依赖：内部 flash 的写路径还没开（`HAL_FLASH_MODULE_ENABLED` 仍是注释、CMake 未编 `stm32f1xx_hal_flash*.c`）；升级的掉电安全靠 A/B 双槽 + meta 扇区的 magic/CRC/有效槽标志；app 不覆盖自己——写内部 flash 那一段属于 bootloader。

## 4. 不变量（改要重新论证）

1. `BSP_init()` 返回 ⇒ 面板 DISPON、GRAM 已清成黑、两个 bank 就绪；任务不再碰初始化。
2. 任何 `lv_*` 只在 UI 线程；AO/ISR 只投事件。
3. 全静态：新线程自带 `StaticTask_t` + 栈数组，尺寸由高水位定，不靠猜。
4. 投递侧永不阻塞（生产者不被消费者拖住）。
5. 面板时序锁在 ST7789VW AC 规格内：写周期 69.4 ns、读周期 180.6 ns。
6. 我们自己新增/修改的行 ≤ 78 显示列（`tools/check_line_width.py`）。
7. 断言：丢日志可以，卡死不行——统一走复位。
8. **刷屏的等待点是真阻塞，不是自旋**：让出 CPU 给 idle，理由见 §7。
9. **跨任务通道不依赖 RTOS 队列**：AO 事件、UI 收件箱、flash 收件箱都是自建静态环 + 临界区，为的是这套结构能原样搬到别的 RTOS 上。今天 queue.c 进镜像只是 FreeRTOS 软件定时器（节拍源）自带的，不是我们的通道在用；完成通知也一样用 notify 槽，不是队列对象。
10. **面板的"醒透"是一条不可被重试打断、而且**不是定值**的时序**：RESX 焊在板级 NRST 上（不是 GPIO），固件无法单独复位面板；冷上电时 RESX 跟着电源爬，给的是**不合格的复位**（datasheet Note 4），面板因此需要一段时间才能接受清屏——实测 **3018 / 3194 / 3816 ms**，还有一次 **>4563 ms**。变量源未定（最可能是拔插速度影响电源轨的放电起点），调试器在不在也影响（接上更快）。因此 `BSP_lcdInit()` 的做法是**密集探测 + 按最坏情况留余量**：每 100 ms 一次「寄存器表 + 清屏 + 回读」，共 100 次（约 11 s），首次成功即退出——**面板已就绪时只花一次**，所以这个预算不影响日常开机耗时。绝不能用周期性 SWRESET 去砸——手册 §7.4.5 Note 1：NVM 校准（ID、VCOM 等）的加载挂在复位路径上、`tRT` 最长 120 ms，重复复位会不断重启它。**机制仍未定**：已排除 NRST 被拖慢、CH340 脉冲、FSMC 时序临界、排线信号完整性；当前假设是 3.3V 轨上升慢，待量电源轨验证。

## 6. 预算

- 内存：内部 SRAM 64 KB（= 0x10000 = 65,536 B，口径同 ST 链接脚本）。现状（2026-10-12 构建、上板通过；bootloader 落地后 app 从 `0x08004000` 起）：**`bss 57,280 / data 12` ≈ 87.4%**（`_ebss` = 0x2000D9CC，到 RAM 顶 9,748 B），text 179,980（`arm-none-eabi-size build/debug/sm_blinky.elf`）；其中 LVGL 池 24 KB、绘制缓冲 15 KB（240×32×2 = 15,360 B）、UI 栈 8 KB、其余任务栈与静态对象约 10 KB。UI 栈高水位（-O2）剩 **1320 words**，8 KB 很宽裕。扣掉链接脚本要求的 1.5 KB（heap 512 B + MSP 1 KB）后，真正可用的余量约 **8.0 KB**（`_ebss` 到 RAM 顶 9,748 B，扣掉 1.5 KB 保留）——够 flash 热路径那份 1~4 KB 的哑元缓冲，再要大件就得把池或绘制缓冲挪到外挂 SRAM。
- 刷屏（2026-10-09 上板实测，DMA 落地后）：**111.8 ns/像素**（整屏 76,800 px = 8,587 µs）／局部帧中位 **115.8 ns/像素**（8,448 px = 979 µs），另加渲染时间。原来的 155 ns/像素是 **CPU 搬运循环自己的极限**，不是总线价：同一批数据 CPU 搬到内部 SRAM 也要 152 ns/字 —— 而 DMA 搬到内部 SRAM 只要 84 ns/字。详情与七路量具表见 §11。
- FSMC 写访问的**价目结构**（record 49 量具，已退休）：每条访问 ≈ **8 HCLK 固定开销** + 每半字 ≈ **4 HCLK**。于是半字 167 ns/px、**字 112 ns/px**（一次访问两个像素）。原来那条"整屏 5.33 ms 面板下界（69.4 ns/字）"因此**不可达**：那是纯总线周期，FSMC 的 AHB 侧固定开销压在它上面。**杠杆是访问宽度，不是谁在搬。**
- 心跳：B 自适应，`LV_NO_TIMER_READY` 兜底 10 ms。一次全屏重绘会把 UI 线程独占 6~10 ms（≈ 一个心跳周期），这是知情代价。
- 实测（-O2、72 MHz、240×32 条带，`[TIME]` 记录）：一次 LED 翻转引起的局部刷新 = **3 块 / 8 KiB**，`FRAME` 总计 **≈11.9 ms**：我们自己的 flush 1.35 ms，LVGL 渲染 ≈10.5 ms。按块看，方块那块（72×72）flush 0.80 ms；两行字那两块（72×24）各 flush ≈0.27 ms、渲染各 ≈2.2 ms。折算刷屏单价 ≈155 ns/像素（≈11 周期，接近 FSMC 5 HCLK 的下限）。**整屏重绘那一条还没测**（要构造整屏失效才有记录）。
- 前提：构建必须带 `-O2`。同一个刷新在 `-O0` 下要 **29 ms**（渲染 21~25 ms），观感就是「一块一块刷」；`-O2` 后 11.9 ms，肉眼看不出过程。text 也从 257 KB 降到 166 KB。

## 7. 刷屏阻塞点与 idle 的关系

tracer 的出口只有一个：idle 任务里的 `vApplicationIdleHook()` → `SST_onIdle()` → `SM_Tracer_idle()` 把环里的记录泵到 UART。于是**刷屏用什么方式等，直接决定日志还转不转**：

- **自旋**（`while (disp->flushing);` 或自己的忙等）：UI 线程保持 Ready，调度器永远轮不到 idle。系统最忙的那段（渲染 + 刷屏）正好是日志黑掉的那段。
- **真阻塞**（`ulTaskNotifyTake(pdTRUE, portMAX_DELAY)`，由 DMA 完成中断的 `vTaskNotifyGiveFromISR` 唤醒）：UI 线程进 Blocked，此时 Blinky 在等事件、timer 任务在等定时器，**CPU 落到 idle，泵就有时间跑**。

结论：DMA 的价值不只是"把 CPU 解放出来"，它是 **idle 时间片的来源**。反过来说，自旋会让 tracer 静默停摆——环只有 16 帧，满了丢最旧的（`SM_Trace_push` 的 GC 分支），不报错。

两个等待点的性质不一样，别混为一谈：主循环那个是在"没事干"的时候等，让出的本来就是空闲时间；`flush_wait_cb` 是在"有事干、但在等硬件"的时候等，**它是忙路径上唯一的让出点**——同步写的时候它根本不存在（线程正在写总线，没有等待点）。

把窗口换算成可用的量：一条 240×32 的搬运 0.533 ms，UART 按 115200 8N1 算是 86.8 µs/字节，**每个窗口约 6 个字节**，大致是一条小记录的量级；整屏十条 ≈ 5.3 ms ≈ 60 字节。也就是说阻塞点买到的是"刷屏期间还能维持最低限度的可观测性"，不是吞吐。泵本身是逐字节阻塞发送（`SM_Tracer_flush_byte_`，`HAL_UART_Transmit` + `HAL_MAX_DELAY`），一条 8 字节记录要 0.7 ms——它跑在 idle 上，被 UI 抢回去也没关系，优先级摆在那儿。

由此派生两条实现约束：

- DMA 完成 ISR 里只允许 `lv_display_flush_ready()` + `vTaskNotifyGiveFromISR()` + `portYIELD_FROM_ISR()`；绝不调阻塞 API。
- `flush_wait_cb` 用通知/静态二值信号量等待，不写忙等。

以及一条需要提前说清楚的**预期行为**：DMA 落地之前，同步 flush 期间没有等待点，idle 拿不到 CPU——所以"整屏重绘时串口静默一会儿、重绘完记录成批涌出来"是设计结果，不是故障。

### DMA 落地后（2026-10-09，已上板）

- 刷屏的等待点**是真阻塞**（`ulTaskNotifyTakeIndexed(1, …)`，20 ms 超时或 DMA 报错 → 线程里断言），本节开头那条"让出 CPU 给 idle 泵"因此达成。让出点确实在用：启动那簇 12 条记录的到达跨度 40.0 ms = 纯线路时间（10.4 ms）的 3.84 倍，说明泵在帧内就跑起来了；短帧上看不出来，因为帧间还有 485 ms 空档供排空（见下一条的线路节拍限制）。
- 观测性要按线路节拍读：记录没有时间戳，主机侧到达时刻的分辨率被 115200 限住 —— **0.868 ms/记录**。所以"泵在帧内跑起来了没有"在短帧上看不出来（局部帧只产 5 条记录，帧间还有 485 ms 纯 idle 供排空）；长帧上看得出来（整屏那帧 12 条记录跨度 > 线路时间）。
- 别拿 GRAM 回读做任何判据（§11 坑 3）。
- **疑似`日志被毁`：现象确凿、机制未明**（2026-10-09）。两次把探针跑密后，一段 32 KB 的抓包**解析出 0 条记录**，而板子显然在跑（记录在流），把探针限速后同一固件解析出 2,284 条。**代码事实（已核）**：记录只在完整时才入环（`SM_TRACE_END` 才 `SM_Trace_push`）；池空时`getBlock` 返回 NULL、`push(NULL)` 是空操作 ⇒ **只丢整条、不写半条**；泵把块取走后该块既不在环也不在空闲表 ⇒ **泵手上的记录不可能被回收重写**；环与空闲表的改动全在 `taskENTER_CRITICAL` 内。⇒ **tracer 结构上不会撕帧**，所以`丢最旧落在泵写到一半`那条我早先写下的说明是**错的，已撤回**。
  工具能力（`tools/trace_read.py`，同一份 294 条好抓包打坏实测）：**2026-10-09 起照抄 `sm_tracer_tui` 的 `HdlcParser` 策略重写**（逐字节状态机：任何 flag 重开一帧、长度先验证再收载荷），存活率从 丢 0.1% 83%→99%、丢 1% 48%→90%、丢 5% 35%→62%、坏 5 字节 24%→98%；纯随机字节仍是 0。⇒ **局部损坏只会按比例丢记录，掉不到 0**；**解出 0 条只可能来自整段系统性错位**，于是早先那句`最像主机侧采集丢字节`也撤回。真正能造成持续错位的机制，这个固件里只有一处：**UART 有两个写者** —— 泵（idle 任务）逐字节写，而 `SM_onAssert` 直写（`__disable_irq()` 只挡中断、挡不住 idle 任务）。断言循环会让两边互相切刀，谁都没有合法帧，这与全部观测吻合（记录在流里、定界符密度正常 17.5% vs 17.6%、限速即恢复），但**未证实**。另一侧参考实现 `sm_tracer_tui` 更健壮，解析问题以它为准；要定案只需固件侧记一个`push 了多少条`的计数，与主机解出的条数对照。

### UI 线程时间线上的占用点

宏观看，程序里只有两个「慢点」，而且**都在 UI 线程自己的时间线上**：`Ui_post*` 永不阻塞，所以它们只拖慢 UI 的响应，不会把别的线程拖住（除了抢 CPU 让 idle 泵变慢）。

1. **刷屏循环**：渲染（CPU 计算）+ 搬运（总线）。一条 240×32 = 渲染 + 0.53 ms 总线；整屏十条 ≈ 5.33 ms 总线加渲染。
2. **flash 读**（热路径 flash → SRAM）：按块分片，每片约几毫秒。

但「慢」有三种性质，后果完全不同：

| 性质 | 线程状态 | 对 idle（tracer 泵所在） | 用在哪 |
|---|---|---|---|
| **真阻塞**（`ulTaskNotifyTake` 之类） | Blocked，让出 CPU | 有时间片 | 主循环空闲等待；将来 DMA 刷屏的等待 |
| **纯工作**（渲染、CPU 逐字写总线、flash 分片读） | Ready，占着 CPU | 该段时间被饿死 | 刷屏与 flash 读的当前形态 |
| **自旋**（忙等标志位） | Ready，CPU 被焊死 | 饿死 | 禁止（§4 不变量 8） |

精确说法：**UI 线程的忙路径上有两段搬运/等待（刷屏、flash 读）加一段计算（渲染）**，每一段都必须是有界的或真阻塞的。别把渲染漏在预算外——它和刷屏同链路，量级可能还大于总线。

真正占住线程 99% 的是 `BSP_flashWaitReady_` 的**自旋**。两件事**都已落地（2026-10-10，已上板，见 §12 写侧）**：① payload 走 TX DMA（`BSP_flashProgramPageDma`）；② 擦除拆成 `BSP_flashEraseSectorStart()` + 轮询、应用侧 `Sm_Flash_waitReady_()` 让出式等器件（`vTaskDelay(1)`；BL 不链 FreeRTOS，所以等待策略留在应用层）。**实测**：擦除 167 ticks、跨页 300 字节写回读全对、擦除窗口内 idle 照跑（`nFree = 16`，夹进 4 条记录）。**剩下的**：AO_FLASH 的请求语义与状态机（记录格式、扇区归属、谁合并谁落盘）—— 那是下一轮设计。
   **后台预擦的触发方式已定（2026-10-10）**：由 **AO 的 `TIMEOUT_SIG` 节拍泵动**（固定频率检查、需要就擦），形状与现有 beat 一致（`BLINKY_TIMEOUT_SIG` + `SST_TimeEvt_arm`）。**分工必须保住**：**检查在 AO**（RAM 水位比较、几微秒 ✓），**擦除在 flash 线程**（发一笔请求过去 ✓）——**不能在 AO handler 里直接擦** ✗：167 ms 的长活儿正是本仓记过的坑（AO 的 8 格队列堆积 ⇒ `sst` 断言复位；flash 自检当初就是因为这个才搬进独立任务）。粒度上 beat 500 ms 远超需要（32 B/s 时填满 4 KB 扇区要 ~128 s ⇒ 检查频率比需要勤两个数量级，成本是几条 RAM 指令 ✓；反应延迟 ≤500 ms）。**状态：暂不实现**（2026-10-10 决定）。
   **2026-10-10 补：擦除命令由谁发**（讨论后的结论）——**仍是 flash 线程**，不是 AO：AO 一旦自己发 SPI 事务，运行期就有两个总线用户 ✗（§3.1 那条"总线不可分割"）。但**形状上等价于"AO 发完就释放"**：AO 的 `TIMEOUT_SIG` 只 post 一笔请求（µs 级 ✓），flash 线程收到后 `BSP_flashEraseSectorStart()`（现成的、启动即返回 ✓），**把"等器件好"推迟到下一笔请求到来之前**（让出式 ✓）⇒ 空闲时不浪费任何等待，器件忙的 167 ms 期间来的请求就排在收件箱里。**水位就是后台擦除的开关**：收件箱空 ⇒ 大胆擦；水位在涨 ⇒ 先别擦。队列深度当前 8 个指针 ✓，建议给收件箱加一个 `nMax` 水位计数（两行）让"要不要做大"有数可依。另一条等价偷懒写法：后台擦除单开一个任务（照 `fwt` 自检任务的形状：优先级 20、静态栈），flash 线程主循环一行不改 ✓。 **注意那份模板只能照形状、不能照干活方式**：作为模板的 `fwt` 自检任务**已于 2026-10-10 移除**（它是全仓唯一的「第二个总线写者」，且整片扫会擦掉资产；见 `bsp_flash.c` 的墓碑注释），当年它自己直接驱动 SPI2（擦+写）⇒ 后台擦除任务照抄它的**静态 TCB/栈 + 一次性创建 + 优先级 20（压在 AO 24 / UI 23 / flash 23 之下）+ 循环里切片让出（`vTaskDelay(1)`）+ 结尾 self-parking** ✓，但**必须走 `Flash_eraseSector()` RPC** ⇒ 它是个**节奏器**、不是工人：循环「挑下一个该预擦的扇区 → 阻塞式 `Flash_eraseSector()`（阻塞的只是它自己 ~170 ms、CPU 交给别人 ✓）→ 睡」，零新机制 ✓。**状态：暂不实现**（2026-10-10）。
   另需一并定：新 op（`FLASH_OP_ERASE` / `FLASH_OP_WRITE`）走**同一条 RPC** 与同一条"缓冲借用"语义；boot/BL 侧继续用自旋版（BL 没有调度器，不能阻塞——与读侧"boot 自旋、运行期阻塞"同一个拆分理由）；
**扇区归属**要先划（资产占 `0x00081000` 起的三槽区，约 460 KB，写者不得碰）。
7. **绘制单价（2026-10-09 实测，已结案）**：同一 72×72 方块扫半径 —— `radius 0` 1,106 µs、`12` 3,673 µs、`LV_RADIUS_CIRCLE` 4,774 µs。两点解出：**简单行 ≈ 213 ns/px，掩码行 ≈ 920 ns/px（4.3×）**；两点模型对 `radius 12` 偏乐观（预测 2,329 µs vs 实测 3,673 µs），说明圆角并不只让上下 `rout` 行走掩码。
   同一轮还量了：**无事可做的 `lv_timer_handler()` 只要 6 µs**（帧时全部是像素，没有可观的固定开销）；**标签块（h=24）≈ 1,900 ns/px**，比整行掩码还贵 —— 字形走的是掩码路径。⇒ 局部帧里最值得动的两处：**圆角（−2.6 ms/次）** 与 **标签重绘频率**。

已定（2026-10-01）：**运行期 flash → SRAM 热路径保留，形态精简为「整个项目共享背景」**——不引入运行期预取、迁移图出边分析、作废与替换策略。背景在启动期一次性搬进外挂 SRAM（若走图片形态），之后切屏恒定命中。

已定（2026-10-01）：**背景形态三种全保留**——纯色／垂直渐变／整屏图。它们在 LVGL 里**本来就是同一个对象上的三个 style 属性**（`bg_color` / `bg_grad_*` / `bg_image_src`），不是三套机制，所以并存只需要"一个描述符 + 一个 setter 分三支"；切屏路径、脏区重绘、UI 循环都不受影响。

这条带来一个意外收益：**纯色与渐变让「每页背景不同」变成零成本**（资产 0 字节、SRAM 0 字节），于是原来"3 张图覆盖不了 10 个页面"的问题消解了。设计包线：

- 默认：每页自己的纯色或垂直渐变（零资产；`LV_GRAD_DIR_VER/HOR` 可用，依据见上一条）
- 例外：需要"照片级"观感的少数页面走整屏图，≤ 3 张，启动期预载

两条实现事实（源码读出，**待一次编译验证**）：

- **背景图不需要 `LV_USE_IMAGE 1`**：`bg_image_src` 在 `core/lv_obj_draw.c:118-140` 处理（含 symbol、recolor、tiled），无该宏门控；它只门控 `widgets/image/lv_image.c`（widget 本身），而 `draw/sw/lv_draw_sw_img.c:15` 只被 `LV_USE_DRAW_SW` 门控。故 `lv_conf.h:78` 保持 0。
- **平铺是原生的**：`lv_obj_draw.c:134` 读 `bg_image_tiled`，所以"条带图 240×32 平铺"无需自定义代码（视觉上每 32 行重复，只适合垂直无缝纹理）。

SRAM 布局：背景槽只在资产表里存在"图片形态"条目时才占位，槽数 = 编译期常量，**0 张图时图标区吃满 1 MB**；不做动态分配。

增量切法：**A** 先做描述符 + 纯色/渐变（0 资产，立刻可上板看）；**B** 再加图片形态（启动预载 + `lv_image_dsc_t` 指向外挂 SRAM）。A 的接口在 B 里不变。

已定（2026-10-01）：**绘制路径是设计约束，不是配置项**。大面积必须走廉价路径（不透明图拷贝 ≈0.1 µs/px），掩码／AA 路径（≈1.2 µs/px，两个都是混合均值、未拆分）只用于小面积。源码依据：

- `lv_draw_sw_fill.c:64-70`：`radius == 0` 且无渐变 = 最简单路径，一次 blend。
- `lv_draw_sw_fill.c:89-93,153,260-269`：有圆角时**只有上下各 `rout` 行**（`rout = min(radius, 短边/2)`）走掩码，**中间段 `mask_buf = NULL`**。故掩码占比 = `2 × rout / 高度`：胶囊按钮与 `LV_RADIUS_CIRCLE` 是 100%，扁宽控件加圆角很亏。
- `lv_draw_sw_arc.c:113-114,186-188`：弧的代价是**整个包围盒**逐行 `mask_apply`，不是可见环；`:159` 圆头端点还会 `lv_malloc(width²)`，width 大时有吃光 24 KB 池的风险。
- `lv_theme_default.c:285-288`（`lv_button`）、`:606-608`（`lv_led`，width 15）自带阴影，走 `lv_draw_sw_box_shadow.c`，比掩码更重。裸 `lv_obj` 没有。
- 渐变：`LV_GRAD_DIR_VER/HOR` 不受 `LV_USE_DRAW_SW_COMPLEX_GRADIENTS` 门控（`lv_draw_sw_fill.c:172,177,274,277`），该宏默认 0（`lv_conf_internal.h:653`）→ **垂直/水平渐变可用且零资产，径向/锥形不可用**。

已定：LVGL 池 **24 KB** 与绘制缓冲（15 KB）**都放内部 SRAM**，沿用现在的 `lv_conf.h`；外挂那 1 MB 留到 DMA 那一步再连总线争用一起设计。UI 线程栈 **8 KB**（LVGL 建议 > 8 KB，实测高水位 914 words）。

已定：**节拍源暂时保持 FreeRTOS 软件定时器**（`SST_sysTimer` + `SST_TimeEvt_tick`），不动 sm_sst。它连带把 queue.c(≈5.3 KB)、timers.c(≈2.7 KB)、定时器任务栈 1 KB、队列对象/存储 240 B、队列注册表 64 B 拖进镜像，约 8 KB flash + 1.4 KB RAM。真要收这笔账，路径是 **SysTick tick hook**（每 10 tick 一次，比软件定时器更准，且 HAL 时基是 TIM1 不冲突）+ 给 sm_sst 加 ISR 版 tick（端口里的 `SST_Task_postFromISR` 已经有了），并关掉 `configUSE_TIMERS`。触发条件：OTA 双槽让 flash 变成稀缺资源，或者需要比软件定时器更准的节拍。

注意 `HAL_Delay` 是**忙等**不是阻塞：它现在无害，只是因为跑在调度器起来之前；挪进任务会以优先级 23 占住 CPU 250 ms，把 idle 时间片和 tracer 泵一起饿死（见 §7）。

## 9. 风险

- LVGL 软件渲染耗时很可能**大于**总线时间（F103 无 FPU/DMA2D）→ 全屏重绘可能吃掉一整个心跳周期，必要时分帧。
- 外挂 SRAM 与 LCD 共用 FSMC：DMA 与 CPU 争用，选 §8.1 时要一起算。
- `LV_OS_NONE` 没有锁：跨线程调用 `lv_*` 是静默损坏，不报错。

## 10. 启动器与资产链路（2026-10-08 落地，已上板）

**镜像布局**：flash 前 16 KB 是 bootloader（`bootloader/`，自带 `stm32f1xx_bl.ld`），app 从 `0x08004000` 起。两份 `.ld` 用同一公式在 RAM 顶端留 32 B 跨复位标志（`_noinit_base = ORIGIN(RAM)+LENGTH(RAM)-32`，`_snoinit` = `0x2000FFE0`，MSP 从它往下长所以永不覆盖）。**CPU 复位永远从 `0x08000000` 取向量 → 只烧 app 不烧 BL 就起不来**，`tools/flash.jlink` 两个 hex 都烧。

**BL 现在做什么**：时钟 → UART1（收发 115200）→ 读标志 → 200 ms 窗口 → 校验 app 向量表 → 交接；标志命中则停在烧写模式，跑「握手 → 分块 → 最终整张 CRC → 擦写 NOR → 读回 memcmp → 写资产头」，写完清标志、`NVIC_SystemReset()` 自己去跑 app。text 9.4 KB / 16 KB，裸机（不链 FreeRTOS/LVGL/sm_sst）。

**资产链路**：PC 脚本（`tools/burn-asset.py`，Windows 侧跑，pyserial + J-Link）→ 串口 → BL → NOR（`assets` 区 `0x00081000` 起：头 1 扇区 + 3 个固定 153,600 B 槽位）；app 启动时读头 → 载荷搬进外挂 SRAM（`0x68000000`）→ 对 **SRAM 副本**算 CRC32 与头部比对 → LVGL 用 `lv_image` 直接指 SRAM 当整屏背景（1:1 直拷贝，不拷贝不解码）。

**实测**：单张 153,600 B ≈ 22 s；三张 460,800 B ≈ 66 s（115200 串口约 40 s，其余是擦除/编程/回读）；最终校验三方一致（脚本 / 目标机 / Python `zlib.crc32`）；`--corrupt-block` 验过重传路径且坏块不折进运行 CRC。代价：`LV_USE_IMAGE 1` 让 app text +5,980 B（168,844 → 174,872）。

**资产图按 RGB565 格点设计**（详见 AGENTS.md）：颜色取 8/4/8 整数倍、形状用几何、光晕用同心环 → 零量化损失（生成器带断言）。源在 `docs/diagrams/sketches/gen_bg.py`，三张：bg-a 六环光晕 / bg-b 网格+细斜线 / bg-c 宽横带+地平线；`UI_BG_SLOT` 一行切换。

**面板 BGR 位**：`MADCTL` = `0x08`（实测定位，见 AGENTS.md —— 这个 bug 从第一天就在）。

**还没做**：① 资产表（每张带自己的长度/CRC —— 尺寸固定时槽位够用，尺寸不一才需要）；② 运行期页面切换（要输入设备）；③ NOR 的读回校验只到「块级 memcmp」。

## 11. DMA 刷屏（2026-10-09，已上板）

**形态**：刷屏走 `DMA1_Ch6` + M2M。源是 LVGL 的 strip（内部 SRAM），目的是面板数据口 `0x6C000800`；**目的地址必须不动**（MINC=0），源递增（PINC=1）。偶数像素且源 4 字节对齐走**字**（一次访问两个像素），否则半字。arm 走 `HAL_DMA_Start_IT`（大小位先 `MODIFY_REG`：HAL 只写地址/长度/中断使能，不重编 CCR），完成走 `DMA1_Ch6` 中断，等待是**真阻塞**（`Ui_dmaWait_` 用 `ulTaskNotifyTakeIndexed` 等槽 1，20 ms 超时或 DMA 报错 → 线程里断言）。代价：text 174,872 → 176,036（+1,164 B），bss 57,016 → 57,088（+72 B）。

**数字（上板实测两轮一致）**：

| | D0 同步 CPU 写 | D1 半字 DMA | 采用（字 DMA） |
|---|---|---|---|
| 整屏 flush | 12,991 µs / 169.2 ns/px | 12,986 / 169.1 | **8,587 µs / 111.8 ns/px** |
| 局部 flush | 1,446 µs / 172.2 ns/px | 1,495 / 177 | **979 µs / 115.8 ns/px** |
| 整屏帧时 | 54.98 ms | 54.98 | **50.47 ms** |
| 局部帧时 | 15.05 ms | 15.05 | **14.59 ms** |

**价目结构**（record 49 量具，已退休，id 不回收）：每条 FSMC 访问 ≈ **8 HCLK 固定开销** + 每半字 ≈ **4 HCLK** → 半字 167 ns/px、字 112 ns/px。CPU 逐字路径是 **152 ns/字**（搬到内部 SRAM 同价 ⇒ 它受循环本身限制，不是总线），DMA 自身 M2M 速率 84 ns/字（6 HCLK，不是瓶颈）。**所以"CPU 换 DMA"在半字路径上一分不省；杠杆是访问宽度。** 原 §6 那句"整屏 5.33 ms 面板下界"因此**不可达**（那是纯总线周期）。

**坑 1（真凶，已修）**：M2M 下 HAL 把源放 `CPAR`、目的放 `CMAR`（`stm32f1xx_hal_dma.c:858-884`）。第一版两个 INC 位都开 → 目的地址每 `0x800` 字节递增一次，而面板的 RS 就是 `FSMC_A10` = `HADDR[11]` → **每 1024 个像素 RS 被翻成"命令"**，窗口寄存器被像素值打乱 → 画面彻底失控、复位无效。证据不是回读，而是**外挂 SRAM 显影**：8 个已知字搬过去，目的只收到最后一个值、其余为 0 ⇒ 源走、目的不动。另：F1 的 `CCR` bit6 = 源侧递增、bit7 = 目的递增（与"PINC/MINC"的字面直觉相反），以寄存器读出与显影实验为准。

**坑 2（已结案：真凶是 RS/1024 与探针，HAL arm 的指控撤回）**：最早那次"画面失控"= 目的地址递增导致 RS 每 1024 像素翻成命令（坑 1）；后来几次可见的损坏，逐条回看都有别的解释 —— 品红方块那版是我**象限探针连续 arm 不等**触发断言（6 次复位，面板留在半个窗口）；"背景花"那版是**诊断图案铺满全屏**。当时把"中断 + 通知"和"HAL arm"一起换掉，于是把因果错记在 arm 上。

考古的三条证据（都不靠眼睛）：
1. **句柄按编译器真偏移读出**（本构建 short-enum ⇒ `Lock` 1 字节、`State` 在 +33、`ChannelIndex` 在 +64）：`Instance` ✓、`XferCpltCallback`/`XferErrorCallback` ✓、`DmaBaseAddress`=DMA1 ✓、`ChannelIndex`=20 ✓ ⇒ "HAL 清错通道标志"不成立。
2. **"早唤醒"探针**（唤醒返回后查 `CNDTR` 是否仍非 0 —— 非 0 就等于线程提前 `flush_ready`、LVGL 把下一块渲染进缓冲、画面撕裂）：寄存器 arm 与 HAL arm **都是 0 次** ⇒ 撕裂不是机制。
3. **变体 H**（HAL arm，其余与已知好版本完全一致）：0 断言、局部 flush 120.1 ns/px（寄存器版 119.1）、目视正确 ⇒ 两条 arm 在可观测层面无差别。

**结论**：arm 用 `HAL_DMA_Start_IT`（簿记更全）；**硬约束只有坑 1 那条（目的地址必须固定）**。方法论教训：当时两个变量（arm 与等待）是一起换的，又把一句目视反馈当成因果 ⇒ **一次只改一个变量**。

**坑 3（方法论）**：面板 GRAM 回读**彻底不可信** —— 用非周期图案做 A/B 时，连 CPU 自己的写入都判 45% 不符。三次探针失效的原因各不相同：①"8 点黑/非黑"对值损坏不敏感；②纯色铺满对相位错位是瞎的；③周期 8 行的图案与 8 行分块共振。**能信的只有：J-Link 读内存、缓冲内的统计、以及人的眼睛。**

**验证资产**：`tools/trace_read.py --gaps/--raw`、`tools/reboot.jlink`（只复位、从 t=0 抓启动记录）、`docs/diagrams/ui-flush.html`（刷屏策略时序图）。

**下一步**：① 局部帧渲染 13.5 ms vs flush 0.98 ms —— 杠杆在渲染侧（§8.6 的 `radius` 扫描）；② 若要机制答案，按坑 2 末尾的逐项回加法做一轮考古。

## 12. flash 运行期读走 DMA（2026-10-10，已上板）

**形态**：`BSP_flashReadDma()` 一次 arm 搬一块（≤ `FLASH_DMA_CHUNK` = 32 KB；DMA1_Ch4 = SPI2_RX 外设→内存、Ch5 = SPI2_TX 内存→外设，都按字节对齐、NORMAL、高优先级），**一块就是一次完整事务**：CS 拉低 → 命令 + 3 字节地址逐字节 → `HAL_SPI_Receive_DMA()`（主/双线模式下它内部就是"同缓冲收发"，不需要 0xFF 假数据）→ 通道中断里拉高 CS 并回调。flash 线程 `Sm_Flash_readDma_()` 循环分块，**块间阻塞在自己的槽 1** 上。boot 路径（`Asset_load()`）保持阻塞版：调度器之前中断关着，中断驱动的路径在那里无法完成。

**数字**：命令/地址仍逐字节，数据段分块（步骤 A，已上板）—— 同址重测三条路径（2026-10-10，48 KB × 4 次、tick 计时、`bad = 0`）：逐字节 **4.8 µs/B（0.21 MB/s）** / HAL 轮询块读 **1.71 µs/B（0.43 MB/s）** / **DMA 0.44 µs/B（2.28 MB/s = 18 MHz 线速）** ⇒ 步骤 A 买 2.8×、步骤 C 再买 3.9×；旧那对「458/196 ms、2.35 MB/s」是 TIM1 回卷口径污染的产物，**作废** ✗。代价：text 174,136 → **176,844**（+2,708 B）、bss 57,104 → **57,264**（+160 B），含故障转存工具，未拆分。

**验证**：① 临时探针逐字节比对 DMA 读与阻塞读（1024 B：不符 **0**、回调 **1** 次；探针已退休，id 65 不回收）；② 当时的常态检查 = 第 60 拍读资产头，**记录 46 = `01 41 53 54 31`**（`AST1` ✓；该探针 2026-10-10 删除，读路径暂无运行期调用者，源保留）；③ 断言 0、故障 0、第 60 拍不再复位。**已实测（2026-10-10）**：擦除窗口里 idle 照跑 —— 两条标记之间夹进 **4 条记录**，且 tracer 的 `nFree = 16`（空闲块满着）；同一位置换成自旋则是 `nFree = 0`、记录被静默丢弃。所以「让出式等待换 CPU」这条现在有数字了。

**写侧（2026-10-10，同一批）**：`BSP_flashProgramPageDma()` 一次 arm **一页**（≤256 B，页对齐、不跨页，护栏与阻塞版相同），一次事务 = WREN → 0x02 + 地址 → `HAL_SPI_Transmit_DMA` → 完成中断拉高 CS。钩子是 **`HAL_SPI_TxCpltCallback`**（`SPI_DMATransmitCplt` 调回调前等 TXE+BSY，所以此刻拉 CS 正确），且 HAL 在双线模式下**自己清 OVR** ⇒ **不需要假 RX 缓冲**。**等待策略不在 BSP**：只给 `BSP_flashIsReady()` 一次轮询，因为 `bsp_flash.c` 也被 bootloader 链、而 BL 没有 FreeRTOS。验证：探针（已退休，id 68/69/70/71 不回收）= 最后 4 KB 扇区上 擦 → DMA 写 → 让出式等就绪 → DMA 读回，两轮：**整页 256 B 不符 0/256**；**页内偏移 8 处写 5 字节、窗口其余保持 `FF`、跨页请求被拒**（`len` 1..256、任意页内偏移，上限是「不跨页」）。**副作用发现**：第二轮的收尾记录被 tracer 静默丢弃（读目标 RAM 得 `nFree = 0`）⇒ 探针式验证要另开 RAM 结果块给 J-Link 读；且 CPU-bound 的擦除自旋能把 idle 泵饿穿，这是 §8.6 ②「让出式等待」的实测理由。代价：**0 B → 1,128 B** —— 拆掉探针后这三个入口一度无人引用、被 `--gc-sections` 整段丢掉（text/bss 与改动前逐字节一致）；运行期写路径落地后它们真的进镜像了，text 176,844 → **177,972 B**。

**器件时间实测（2026-10-10，阻塞 BSP 计时，各 16 次采样）**：

| 操作 | 实测 | 手册（W25Q128BV Rev E） | 判读 |
|---|---|---|---|
| 4 KB 扇区擦除 | **165…170 ms**（均值 166.6，±1.5%） | 30 ms 典型 / 200 ms 上限（<50k 次） | 慢 5.5×，但**极稳定且合法** ✓ |
| 256 B 页编程 | **551…580 µs**（均值 ~565） | 字节模型 30 µs + 2.5 µs/字节 ≈ 668 µs | 实测比模型还快 ~15% ✓ |
| 1 字节程序（调用侧） | 63 µs | 器件首字节 30 µs | 差值 = 协议开销（WREN + 状态读 + CS 周期） |
| 5 字节程序（调用侧） | 115 µs | 器件 ~40 µs | ⇒ **小记录写入由协议开销主导**，不是 tBP |

**方法学**：用**阻塞**版 BSP（自旋、无任务切换）⇒ 调用者能自己计时；擦除用 tick（1 ms 够），页编程用 TIM1 的 CNT（1 µs）。**但 CNT 的 `ARR = 999`、每 1 ms 回卷**（J-Link 直读 `0x40012C28 = 0x47`、`0x40012C2C = 0x3E7` 核实）⇒ 只有**短于 1 ms** 的量能直接差分，长量必须配 tick —— 第一轮那批"65,0xx µs"就是这么来的（按 1 ms 周期还原后全部落回 551…580 µs）。

**四个坑**（详见 AGENTS.md，全部由**故障转存**定位）：`__HAL_LINKDMA`（`Parent` 为 NULL ⇒ 野指针 ⇒ IMPRECISERR）、完成钩子是 `HAL_SPI_RxCpltCallback`（`BUSY_RX` 分支）、完成回调里不许再 arm（分块交调用方）、使能 NVIC 前必须先有向量（否则 `Default_Handler` 死循环、静默停机）。


## 13. Flash 接入 SST AO（2026-10-23，历史方案）

- 目录：application/aos/flash/；IO/请求适配在根下，状态处理在 hsm/。
- AO_start 统一调用 Flash_ctor 和 SST_Task_start，然后启动 Blinky。

## 14. Flash 对象与运行时 operations（2026-10-23）

BSP 持有唯一 BSP_Flash 对象，对应 SPI2 上的物理器件。
所有公共读写擦都接收对象指针；不复制对象、不另建总线访问者。

- operations：BSP 提供 Poll/DMA 两张常量表，包含有界读、页编程、
  扇区擦除命令。两表复用命令、地址、状态和 CS helper。
- waitOperations/context：应用提供完成消费、通知、延时、块间让出，
  以及现有时基的读取和差分换算。BSP 不依赖 FreeRTOS 类型。
- Poll 的完成回调同步发生；DMA 在中断完成，启动失败则同步回调。
  均在 CS 收尾、硬件停止使用缓冲后恰一次通知，允许先通知后等待。
- 公共方法负责完整分块/分页与芯片 BUSY 等待，返回时完成语义一致。
  program/erase 原语完成只表示命令/传输结束，不等于芯片内部完成。
- busy 覆盖完整公共操作，包括页/块间让出和器件 BUSY 轮询。
  无在途操作、无 DMA、无未消费完成且器件就绪，才允许旧所有者换绑。
  丢失完成仍 fail-stop；普通传输/设备失败返回 false。

| 传输表 | 等待策略 | CPU 行为 |
|---|---|---|
| Poll | 忙等 | 块内 CPU 轮询；完成标志同步消费 |
| Poll | 让出 | 块内仍轮询，块间和芯片 BUSY 等待可让出 |
| DMA | 忙等 | 中断完成，调用者忙等标志 |
| DMA | 让出 | indexed 通知阻塞，BUSY 间隔让出 |

擦除无数据段可搬运，DMA 表的 erase 复用轮询擦除命令实现。
芯片内部擦除靠 BUSY 判定；擦除独立方法槽保留替换实现的空间。

AO Flash 同时拥有初始化与运行期的静态等待表、上下文：
先绑定 Poll + 初始化标志，挂载/恢复 NVS，再绑定 DMA + AO 任务句柄。
NVS 的 flash_device 始终是同一 BSP_Flash 指针，port 删除两套后端。
初始化无需调度器通知/中断；运行期槽 0 属 SST，槽 1 等完成。
初始化计时沿用 DWT，运行期沿用 HAL tick；本次未另行修改计时策略。

Asset_load 在自己的代码区持有标志等待能力：header 绑定 Poll，
payload 换为 DMA + 标志忙等；完成后 AO 初始化接管同一对象。
bootloader 在自己的镜像内绑定 DMA + 裸机标志忙等。
BSP 删除无绑定的资产专用读入口，不留绕过对象所有权检查的公开路径。

物理分区：BSP 为硬件初始化、共享协议、POLLING OPERATIONS、
DMA OPERATIONS、对象绑定与公共方法；AO 为 INIT WAIT、RUN WAIT、
LIFECYCLE BINDING。资产与 bootloader 各自的等待能力留在调用层。
